# 低频写入、大存量 NAS 的存储与备份评估

评估日期：2026-11-28。结论是技术选型与隔离实验结果，不是生产迁移决定。现有数据、挂载、数据库位置与网盘格式保持不变。

## 结论

优先验证 **Btrfs 主数据卷 + 有容量边界的只读快照 + 分片、加密的云端增量流**。这是下一阶段候选，不是已经可上线的方案。它把变更识别交给文件系统，较适合单机、低频写入、大存量，也避免自行实现所有应用都必须依赖的文件系统代理。

如果后续明确需要文件级事件订阅、跨节点访问或对象存储接口，再评估 SeaweedFS。JuiceFS 的对应 Changelog 能力仍标为 Beta，不以该功能作为当前个人 NAS 的唯一可靠变更来源。ZFS 可作为未来原生 Linux 的候选，当前 WSL 尚未发现已安装的工具和模块，不为本评估更换共享 WSL 内核。

## 需求解释

1. 本地不维持完整第二份用户数据；允许有界元数据、缓冲与必要的短期旧块。云端允许版本和适量冗余。
2. 允许牺牲部分写入速度，换取持久、可追溯的变更管理。写入确认不等待云盘；备份故障、断网或限流不能阻塞业务。主文件系统自身故障仍可能影响应用，不能承诺存储零故障。
3. 正常增量的主要工作量与本次变化及关联元数据有关；不能每轮全目录扫描、加载全部历史或重导出全部数据库。首次基线、故障重建、低频检查和恢复仍有规模成本。
4. 改造依据应用注册表中的资源和能力，不能按应用名写分支；数据库与普通文件采用适合各自资源类型的恢复机制。

## 实际环境与评估边界

- 主数据位于 NTFS，经 WSL 的 DrvFS/9p 暴露给 Linux。当前不是原生 Btrfs/ZFS 数据卷。
- `/dev/fuse` 存在。当前 WSL 提供 Btrfs 内核模块；隔离实验已成功加载并使用该模块，不需要更换内核或取得 Windows 管理员权限。
- 生产数据库继续位于内置盘中的既有 Linux 文件系统镜像。没有将数据库迁回 USB 数据盘。
- 内置盘容量和 WSL 可用内存有限。评估没有安装系统软件包、构建大镜像或下载大体积测试数据。
- 实验使用包索引中校验过 SHA-256 的 Ubuntu btrfs-progs 6.17.1 工具，解包到 `/run`，不加入生产安装。
- 测试在独立 mount namespace、256 MiB tmpfs 中进行，创建两个全新的 512 MiB 稀疏普通文件镜像；CPU 限制 25%，内存上限 512 MiB。未格式化物理盘，也未使用或复制用户文件。

## 候选比较

| 路线 | 日常变化识别 | 本地存储代价 | 新增依赖与限制 | 本次判断 |
| --- | --- | --- | --- | --- |
| Btrfs 快照与 send | 比较只读快照生成变更流 | 共享未变块，保留变化旧块及元数据 | 数据必须进入 Btrfs；需父快照/恢复链及云端分片协议 | 单机优先候选，继续验证 |
| ZFS 快照与 send | 文件系统块级变更记录 | CoW 与历史保留；可研究 bookmark 减少源端历史占用 | 需 ZFS 内核支持；普通网盘不是 ZFS 接收端 | 原生 Linux 后续候选 |
| SeaweedFS Filer + CDC/backup | 订阅 Filer 元数据日志并异步读取文件 | 卷数据、元数据和必要缓冲，需限制复制/缓存 | 接管主存储；Aliyun Drive 非文档列出的直接 sink，恢复/版本语义还需适配 | 有内置连续备份方向，但对单机偏重 |
| JuiceFS + Changelog | 文件系统层记录变更，消费者保存游标 | 数据块与元数据库；缓存、Trash、旧块均需预算 | Changelog 仍为 Beta；日志不含数据，不等于已完成备份 | 暂不作为唯一变更依据 |
| NTFS USN + 增量引擎 | 使用现有卷日志 | 主要为索引与有界日志 | Windows/NTFS 与卷访问权限依赖；日志过期后仍需补扫 | 低侵入过渡路线，不优先作为跨平台目标 |
| 普通目录 watcher + Restic | 事件通知或定期扫描 | 元数据为主 | 通知可能丢失；继续备份整个目录仍有遍历与索引成本 | 可缓解现状，不能满足全部目标 |

依据：[Btrfs send](https://btrfs.readthedocs.io/en/latest/btrfs-send.html)、[OpenZFS send/receive](https://openzfs.github.io/openzfs-docs/Basic%20Concepts/Operations/Send%20and%20Receive.html)、[SeaweedFS CDC](https://github.com/seaweedfs/seaweedfs/wiki/Filer-Change-Data-Capture)、[SeaweedFS Async Backup](https://github.com/seaweedfs/seaweedfs/wiki/Async-Backup)、[JuiceFS Changelog](https://juicefs.com/docs/community/administration/changelog/)、[NTFS USN](https://learn.microsoft.com/en-us/windows/win32/fileio/change-journals)。

### 两个不能忽略的产品边界

SeaweedFS 的异步备份文档列出 S3、GCS、Azure、B2、Local Disk 等目标。镜像模式会传播变更；其按日期增量模式不应用删除，不能直接等同于本项目要求的“最新视图反映删除，同时可恢复历史”。不能因为能接收事件，就宣称已支持阿里云盘及正确的历史恢复。

JuiceFS Changelog 自 1.4.0 起提供、当前文档仍标 Beta，保存的是操作元数据，不是文件内容；消费者停机超过日志保留窗口会出现缺口。其全量元数据 dump 同样具有规模成本，且文档说明一般 dump 不提供完整快照一致性。不能将“换成 JuiceFS”视为自动解决所有备份问题。

依据：[JuiceFS 元数据恢复](https://juicefs.com/docs/community/metadata_dump_load/)、[JuiceFS 元数据库](https://juicefs.com/docs/community/databases_for_metadata/)、[JuiceFS Trash](https://juicefs.com/docs/community/security/trash/)。元数据库/Trash 和缓存也会占空间，不能漏算成本。

## Btrfs 隔离验证结果

测试数据为随机生成的 8 MiB 文件及分布在 32 个目录中的小文件。两组均修改 10 个小文件、覆盖大文件中 64 KiB，并各执行一次新增、删除、重命名。流直接通过有界管道送入另一测试文件系统，没有把完整流保存为本地中间文件。

| 项目 | 1,001 个文件 | 10,001 个文件 |
| --- | ---: | ---: |
| 完整基线流 | 8,780,513 字节 | 12,228,023 字节 |
| 相同类型修改的增量流 | 68,609 字节 | 68,612 字节 |
| 增量发送并接收耗时 | 0.131 秒 | 0.143 秒 |
| 创建并同步基线快照前后镜像实际分配增量 | 114,688 字节 | 147,456 字节 |
| 完整与增量恢复后，逐文件 SHA-256 比较 | 通过 | 通过 |
| 后续修改后，前一恢复点仍可读取且哈希不变 | 通过 | 通过 |

这些数字只验证差分与恢复机制；内存存储、小文件集合和限额 CPU 不代表真实 SSD 的性能，更不能外推 TB/百万文件规模常数耗时。创建快照没有立即产生完整副本，但改写/删除后旧块会继续占空间。

原始报告保存在私有运行目录 `system/runtime/storage-evaluation-20261128.json`，原始日志同名前缀。测试结束后两个临时 loop 均已释放，生产数据库 loop 未改变。原始脚本先尝试卸载 tmpfs 时因 loop 持有文件返回 busy，随后已分离两个 loop，命名空间退出释放挂载；报告保留该过程并注明清理已验证。仓库评估工具已调整为先分离 loop，再卸载 tmpfs。

可复用工具：[verify-btrfs-storage.py](../tests/verify-btrfs-storage.py)。仅手动 opt-in，要求 root、独立 mount namespace、`/run/nas/storage-eval-*` 工作目录及全新报告路径；必须由资源受限的临时 unit 调用，不加入生产启动或自动测试。工具不会下载、安装软件或处理现有镜像。

## 推荐架构（待验证）

```text
应用读写 → Linux Btrfs 活动数据卷
                    ↓ 生成只读检查点，应用继续写活动卷
                文件系统增量流
                    ↓ 小块缓冲、加密、校验
                网盘分片与提交清单
```

1. 所有文件写入通过同一主数据卷；应用可继续使用普通目录接口，不需要调用专用备份 HTTP 服务。
2. 以短周期批量检查点实现近实时，不承诺每次 write 都立即产生一个远端恢复点。上传完成前不能声称已经保护。
3. 初次发送基线，以后基于已确认父检查点生成增量。正常任务不读取全部历史版本，也不使用 Restic 全目录扫描作为外层备份器。
4. 增量流拆成有界分片后上传，不在本地落成完整流文件；只有相关分片均成功且校验确认后才提交远端清单。最后一次完整提交在中断时仍可用。
5. 本地只保留必要检查点，按实际旧块空间预算清理；云端保留历史、基线和恢复依赖。不能仅按“两个快照”就声称空间有界。
6. 备份组件不进入业务同步等待链。网络断开时 NAS 仍运行，备份延后；本地保留达到预算后，可放弃未上传的中间检查点、保留已有云端恢复点，必要时后续重新建立基线。不能同时承诺无限离线历史、零额外空间和完全不影响业务。
7. CPU、内存、I/O 和上传带宽限制优先保障 NAS。目录枚举、云端对象布局及索引也必须避免随历史增长而每轮全扫。
8. 独立展示最近提交和最近校验。频繁提交、低频完整校验、恢复演练各自调度；不把上传成功冒充已验证整个历史仓库。

### 本地空间的准确含义

快照初始共享文件内容，不代表永远不额外占空间。可估算为：

`活动数据 + 仍被保留检查点引用的旧块 + 文件系统元数据 + 有界传输缓冲`

例如保留检查点后把一个很大的文件全部重写，旧块仍可能使占用接近双份。因此本方案满足的是“不主动保存完整第二份数据，并约束旧块保留”，不是任何工作负载下都绝不接近 double。用户是否接受这一明确边界，需在生产方案中写清。

Btrfs 快照与源数据共享底层介质，不能代替异盘备份。[官方快照说明](https://btrfs.readthedocs.io/en/latest/Subvolumes.html)。

### 普通网盘上的恢复和中断

阿里云盘只是保存对象，不运行 `btrfs receive`。需要保存基线、增量分片、父子依赖及加密/哈希信息。恢复到新的 Btrfs 目标时按依赖次序接收，不能随意删掉旧基线。长链需要低频建立新的云端基线，验证成功后才考虑淘汰旧依赖。网盘配额预算须包括旧仓库、新基线、增量和冗余，不能假设可无限保留。

该路线对整卷恢复较自然，但从较长增量链只恢复一个小文件可能仍需重放大量数据，不具有 Restic 文件目录索引的同等便利。必须单独测单文件恢复的下载量、临时空间和耗时；若成本不可接受，需要辅助恢复索引或改选其他路线，不能仅以备份快就认定整体更优。

分片已上传不等于具备原生的流字节偏移续传。中断后可以复用已确认分片，但是否需要重新生成前缀、能否在工具版本变化后稳定续传，都须实验。不能把 ZFS 接收端 resume token 或本地 send/receive 成功，直接说成网盘断点续传已验收。

CRC 不能替代云端对象的加密认证与强哈希检查。接收端只接受经过验证的可信流，并限制恢复目录权限；不能覆盖生产卷。[Btrfs receive 安全边界](https://btrfs.readthedocs.io/en/latest/btrfs-receive.html)。

## 现有 WSL/USB 环境的阻塞项

- 当前 NTFS 目录不能原地变成 Btrfs。后续只能另建受控文件系统镜像，或评估专用 Linux 格式磁盘的接入；本次没有创建生产镜像或格式化磁盘。
- WSL 内对受控新文件镜像进行 loop/mount 已验证不需要每次 Windows 管理员授权；这不证明真实 NTFS/DrvFS 上的刷盘、稀疏空间回收和 USB 故障恢复已经合格。
- 既有 USB 掉线历史必须纳入测试；任何新文件系统都不能修复线材、供电或物理链路的不稳定。
- 镜像方案要同时监测内部空间与外层 NTFS 空间；必须验证 discard/空间回收，避免内层已删除但外层长期不释放。
- 主数据卷挂载失败必须 fail closed，不能把空挂载点暴露给应用后继续写入。启停、卷身份、弹盘、状态页和恢复流程均需适配存储能力，不能仅修改 Compose 路径。

## 数据库与启动依赖

当前共享 PostgreSQL 位置不变。数据卷检查点不包含它，也不保证数据库与附件同一事务时刻。保留已接受的最终一致性边界，数据库恢复采用正式在线机制；完整导出需流式/有界缓冲，基线与日志方案另行验收，不能直接同步运行中的数据目录。

若选 JuiceFS/SeaweedFS 并复用共享数据库做文件系统元数据引擎，必须避免“启动数据库依赖该文件系统、挂载文件系统又依赖数据库”的循环；元数据丢失也可能使完好的块无法解释，必须随数据恢复链一起保护。主数据不以远端云盘可用性作为启动条件。

## 下一阶段验收与迁移门槛

| 步骤 | 具体工作 | 验收标准 |
| --- | --- | --- |
| 1 | 在受控 NTFS/USB 测试位置建立全新实验镜像 | 不涉及生产文件；刷盘、稀疏分配、释放空间、正常卸载和再次挂载结果可验证 |
| 2 | 用固定增量比较不同存量规模 | 记录遍历量、传输量、CPU/I/O、内存、延迟；增量不能退化为每轮全目录/全历史处理，分别测多小文件和少量大文件 |
| 3 | 验证实际文件接口与应用兼容性 | 重命名、删除、权限、文件锁、fsync、并发访问、普通客户端同步正确；资源按声明接入，不添加应用名特判 |
| 4 | 在全新云端测试目录验证分片、提交与恢复 | 保留旧云端仓库；上传中断、断网、重复提交、损坏分片均不能覆盖上一完整点；从云端独立恢复并逐文件比对，测单文件恢复成本与配额预算 |
| 5 | 验证旧块保留与业务优先 | 模拟大文件重写、批量删除、长期断网及低空间；达到预算时备份退让，不能无限保留旧块直至挤满业务盘 |
| 6 | 验证数据库恢复与全机重启 | 已登记数据库和配置均有恢复证据；卷身份、依赖顺序、缺盘和受控关机正确，不伪称跨卷应用一致 |
| 7 | 制定可回退迁移方案 | 指明额外空间与校验方法；安全迁移可能暂需额外副本或外接盘，不能为了省空间先删除唯一来源；未通过恢复验收不切换生产 |
