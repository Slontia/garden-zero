# Btrfs 网盘备份实现

状态：开发与隔离验证中，尚未替换已部署的 Restic 自动备份。原生 Btrfs 数据盘为必要条件；原仓库及其恢复密码继续保留。

## 资源与协议

- 文件：只读子卷快照与 `btrfs send` 基线/增量；正常任务不遍历用户目录、不读取全部历史。已确认父检查点丢失时显式建立新基线，不伪造连续性。
- 数据库：独立物理基线与 WAL 恢复链，覆盖整个已登记共享集群，采用正式 PostgreSQL 复制协议；不复制运行中的数据目录，不逐应用判断。避免无限 WAL slot 保留，不把云端传输置于同步提交路径；缺口检测后重建基线。
- 配置：受限的在线配置/SQLite 捕获，独立资源与提交频率，不混进每个文件增量。
- 传输：提供方无关的对象接口，复用现有 rclone 与账号驱动；新格式写入独立命名空间，保留旧 Restic 仓库。

对象流使用有界分片、scrypt 派生密钥和 AES-256-GCM 认证加密，密钥来源为既有恢复密码。目录/内容信息位于加密载荷，不能降级为明文。固定大小的清单页描述分片；根提交只引用其页与父流。对象及完整流均有 SHA-256；只有生产者成功退出且分片回读验证完成后才发布恢复点。

两份交替 head 保留上一版指针；新提交先写不可变清单、保存本地提交意图，最后更新 head。写 head 中断后可利用本地已验证意图修复本任务的指针，不删除旧版本。SQLite 只保存待上传分片的哈希与游标，设定大小上限，提交后回收记录；不缓存完整用户数据。

恢复必须逐对象认证、验证哈希和父链，并接收到隔离的、未经发布的新目标。不能直接覆盖生产卷。Btrfs 接收对目标文件系统的要求和长链单文件恢复成本须明确保留。

## 效率、预算与边界

日常路径读取固定 head 与本次增量，不全量列举历史；云端对象目录使用三层 SHA-256 前缀分桶（每层两位十六进制），避免通过网盘目录枚举重新引入随历史增长的查找成本。首次基线、恢复与低频完整检查允许规模成本。

只读快照共享未修改的数据，但改写/删除会保留旧块；必须监测真实旧块和数据盘余量，超过预算就释放本地备份引用、延后备份或重建基线。不得用会反向阻止业务写入的硬快照配额掩盖空间问题。云端已提交历史不随本地检查点清理而删除。

中断续传可复用确认过的分片；Btrfs send 在恢复时可能需要重新生成前缀，并非原生字节偏移续传。生产者/内核版本或流内容改变时拒绝静默接续。文件和数据库资源仍采用已接受的最终一致性，不能声称跨资源同一事务时刻。

## 验证与切换门槛

1. 分片协议：加密认证、空/未知目标拒绝、父链、所有上传边界中断、源变化、回滚及有界读取。
2. Btrfs：隔离基线与增量接收，新增/覆盖/重命名/删除及历史保留；不同存量下固定增量的发送量与处理耗时。
3. 数据库：基线与 WAL 重放、角色/多个数据库、时间线/系统身份/缺口与断网，恢复后真实 SQL 校验；证明断网不会导致源端 WAL 无限保留。
4. 真实网盘：独立测试命名空间上传下载、认证失败、限流、断点续传与隔离恢复，保留旧仓库。
5. 宿主：进程 CPU/内存/I/O/网络限制、快照旧块预算、任务取消/关机、多个账号以及前端状态；全部通过后才启用新自动任务。

## 宿主实现与开发入口

新实现按资源拆分为 `nas_btrfs_stream.py`（文件）、`nas_pg_stream.py` / `nas_pg_backup.py`（共享 PostgreSQL）、`nas_stream.py`（提交协议）、`nas_objects.py`（提供方传输）和 `nas_native.py`（编排）。账号继续复用现有授权和自动开关；默认仍为 `restic-online`，只有显式配置 `cloud_backup_engine: btrfs-v1` 才选中新实现。**此开关不是生产验收结论，目前不要直接修改在线实例切换。**

宿主依赖 `btrfs-progs`、systemd、Python `cryptography` 与 `psycopg2`。`native-backup.py prepare` 默认只检查；`--apply` 会登记专用 qgroup、进行首次配额统计扫描，并创建仅用于备份的 PostgreSQL 复制角色及限定来源的 SCRAM 规则，重载 HBA，不重启数据库。首次统计扫描不是日常提交的一部分；它仍会消耗磁盘资源，应单独安排。

上传任务由 `native-backup-worker.py` 在独立 systemd transient unit 中执行：CPU 20% 单核、内存 512 MiB、禁用交换、数据物理盘读取 4 MiB/s / 写入 1 MiB/s、低 I/O 优先级，临时目录最多 128 MiB；传输容器另有限额，网络默认 4 MiB/s。用户数据在工作进程中只读，受管快照目录可写。数据库服务端生成基线的工作仍发生在数据库自身进程内，使用 `pg_basebackup --max-rate` 与 spread checkpoint 控制，不能把工作进程限额说成涵盖所有数据库开销。

默认本地旧块预算为 4 GiB，同时保留数据盘保护线之上 4 GiB 的余量，最多登记 8 个检查点。统计父 qgroup 同时包含活动子卷和检查点，旧块按父组 referenced 减活动子卷 referenced 计算，不对活动数据设置硬配额。后台监控独立于账号自动开关；预算不足时按任务 ID 合作式中断，待退出后仅释放 UUID 匹配的已登记只读检查点。未登记完整身份的异常检查点拒绝自动删除，需显式核查。保留远端已上传提交的发布意图；无可用父检查点时重新建立基线，云端历史不删除。

`native-backup.py inspect --account <ID>` 查询各资源 head；`export-stream --account <ID> --commit <ID> --stdout` 将通过认证的单个流输出到管道，拒绝输出到终端。恢复时先检查 manifest 的 resource / producer / parent：文件增量必须按父链从基线依次 `btrfs receive` 到**隔离的新目标文件系统**；配置是 tar，数据库基线是 PostgreSQL tar，WAL 使用偏移帧，不能混用。输出最后的整体哈希验证失败时，目标仍属于未发布的恢复暂存区，禁止用于生产。该低层入口不是完整的一键恢复器；父链编排、目标发布和异机恢复仍待补齐。

数据库不创建持久复制槽，不改变 WAL 长期保留量。云盘断网较久导致所需 WAL 被回收时会重建基线，不能承诺任意断网时长都只传增量。PG14 恢复到某个提交的 flush LSN 时，只提供该提交之前的 WAL，在隔离实例中重放到所提供有效记录末尾；不能直接把 flush 的记录结束位置当作 `recovery_target_lsn` 的记录开始位置。

## 已获得的验证证据（2026-11-28）

- 独立 Btrfs 文件系统：文件数从 1,001 增至 10,001，相同增量流约 68 KiB；基线、断点重试、独立接收、删除和旧版本保留通过。这是小规模隔离证据，不是任意数据规模的性能保证。
- 隔离 PostgreSQL：官方 `pg_verifybackup` 校验基线，通过 WAL 恢复两个数据库的新增、修改、删除及角色，没有复制槽。
- 真实阿里云盘：独立 `native-test-*` 命名空间完成加密回读、上传中断后重试、基线和两次增量、head 换槽与最早提交回读。仅上传生成的测试内容；保留测试命名空间和旧仓库。该测试不等于生产全量云端恢复。
- 真实 USB Btrfs 盘：仅使用 16 MiB 生成文件，验证 systemd 限额实际生效，写入约 16.2 秒、读取约 4.1 秒；验证工作进程的用户数据只读视图及数据库只读查询，生成文件已清理。

仍需完成完整编排的取消 / 账号并发 / 重启恢复验证、端到端云端隔离恢复与生产就绪检查，再安装切换。原有网盘链路继续使用原格式；不得因这些分项测试就把生产账号标记为新引擎成功。
